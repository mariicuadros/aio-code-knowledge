# AIO CODE — Pre-Pilot Audit

**Audit ID:** AUDIT-2026-09-23  
**Date:** 2026-09-23  
**Scope:** Repository architecture, methodology, evidence model, Observatory, metrics, baseline readiness, intervention traceability, pilot readiness and internal consistency.  
**Status:** ACTIVE — corrections initiated immediately after this audit.

## Executive conclusion

AIO CODE already has a substantial architecture: canonical entity records, entity graph, claim ledger, Observatory, Entity Labs, metrics, provenance, content registries and public-method boundaries. The principal pre-pilot risk is no longer missing architecture. It is **methodological ambiguity and incomplete operationalization**.

The project is ready to move from **architecture** to **evidence and replication**, but it is **not yet ready to claim pilot validation**.

The critical path is:

`Freeze → Define → Baseline → Intervene → Observe → Measure → Compare → Replicate`

## Severity scale

- **P0 — Blocking:** must be corrected before new experimental/public interventions intended for measurement.
- **P1 — Critical:** must be corrected before external pilots.
- **P2 — Important:** should be corrected before commercialization/accelerator diligence.
- **P3 — Later:** useful after validation; not a current blocker.

## P0 findings

### P0-01 — Baseline dataset exists but contains no records

`ai-social-baseline.json` defines fields and entities but currently has an empty `records` array. Therefore it is a baseline schema/container, not a frozen empirical baseline.

**Risk:** post-intervention observations cannot be cleanly compared with a preserved pre-intervention state.

**Correction:** create and freeze `MC-001 BASELINE v1` from standardized Observatory runs. Never overwrite historical records.

### P0-02 — Prompt benchmark is not immutable or ID-addressable

The AI Representation Protocol contains example/benchmark prompts, but they are numbered rather than governed by stable prompt IDs and explicit versions.

**Risk:** prompt drift can be mistaken for entity-representation drift.

**Correction:** establish a versioned Prompt Registry with stable IDs such as `ENT-01`, `DIS-01`, `REL-01`, `SRC-01`, `CAT-01`, `REC-01`; freeze a benchmark version for every before/after comparison.

### P0-03 — Evidence state and claim lifecycle are mixed

The Claim Ledger currently places `defined`, `observed`, `corroborated`, `verified`, `hypothesized`, `unknown`, and `superseded` in one `status_values` list.

**Risk:** `defined` and `superseded` describe lifecycle/record state while `Observed`, `Corroborated`, `Verified`, `Hypothesized`, and `Unknown` describe evidentiary state. Mixing them makes queries and governance ambiguous.

**Correction:** split into at least:

- `claim_status`: active | superseded | withdrawn | draft
- `evidence_state`: observed | corroborated | verified | hypothesized | unknown
- `claim_type`: canonical_definition | research_observation | research_finding | hypothesis | commercial_statement

### P0-04 — `Verified` has no explicit verification rule

Current documents state that evidence strength determines claim strength, but the threshold/authority for promoting a claim to `Verified` is not formally defined.

**Risk:** self-attested first-party claims could accidentally be interpreted as independent verification.

**Correction:** Evidence Standard v1 must define evidence classes, independence, minimum support, verification actor/rule and downgrade conditions.

### P0-05 — Observation schema uses `confidence` as an evidence-state field

`observatory/observation-schema.json` calls the field `confidence` but its enum contains evidence states (`Observed`, `Corroborated`, etc.).

**Risk:** confidence and epistemic/evidence classification become semantically indistinguishable.

**Correction:** rename to `evidence_state`; if confidence is retained, define it separately and never use it as a substitute for evidence.

### P0-06 — Interventions are not governed by a universal Intervention ID rule

The methodology describes interventions, but repository-wide change attribution is not yet enforced through one standard Intervention Record.

**Risk:** multiple simultaneous changes make causal interpretation impossible.

**Correction:** every experimental change receives an `INT-*` identifier with timestamp, entity, target, changed variables, expected effect, related claims, evidence and subsequent observations.

### P0-07 — New public content is already becoming an experiment

The repository now includes an Instagram mother experiment and a 30-day observation window. That makes intervention discipline urgent.

**Risk:** if unrelated entity/schema/content changes occur during the same window without IDs, attribution becomes weaker.

**Correction:** mark confounders and keep a change log for all experimental windows.

## P1 findings

### P1-01 — Two repository namespaces can create internal source-of-truth ambiguity

The repository contains both `/entity/...` and `/entities/aio-code/...` structures.

**Correction:** preserve both only with explicit semantics:

- `/entity/` = canonical cross-entity identity specifications and passports.
- `/entities/<entity-slug>/` = operational per-entity workspace/records that MUST reference canonical identity and MUST NOT redefine it.

Any duplicated identity field must point back to the canonical passport.

### P1-02 — AIO-001 type is not perfectly stable across documents

The project appears as `Research Project`, `ResearchMethodology`, and a research/implementation methodology in different contexts.

**Correction:** canonical type is `ResearchMethodology`; organizational/product status may be described separately. Never use entity type and commercial form interchangeably.

### P1-03 — Recognition is still partially represented as a ladder

The existing R0–R5 representation classification is useful descriptively but combines recognition strength with recommendation at the top.

**Risk:** recommendation is a different behavioral dimension and should not be interpreted as “more recognized.”

**Correction:** replace the single ladder as the primary rubric with orthogonal dimensions: resolution, identity accuracy, attribute accuracy, relationship accuracy, source discovery, citation quality, disambiguation, hallucination, consistency and recommendation.

### P1-04 — Recommendation must remain separate from retrieval/representation

The documentation already states this conceptually, but schemas and public summaries must preserve it consistently.

**Correction:** never roll recommendation into a general recognition score.

### P1-05 — No calibrated external benchmark yet

MC-001 remains the primary longitudinal case.

**Risk:** n=1 and creator/researcher overlap limit generalization.

**Correction:** build a read-only benchmark of 20–30 external public entities spanning unique names, homonyms, multi-project creators and mixed person/brand structures.

### P1-06 — Pilot protocol is not yet a single governed specification

Pieces exist across research architecture, Observatory, Entity Labs and Metrics, but participant input/output, consent, data handling, intervention boundaries and exit conditions are not consolidated.

**Correction:** create `PILOT-PROTOCOL-v1.md`.

### P1-07 — Product claims require a stricter boundary

AIO CODE can presently defend structuring, documenting, auditing, observing and measuring entity representation. It cannot guarantee recognition, recommendation, ranking or control of third-party AI systems.

**Correction:** adopt a public claims boundary: **measure and improve controllable signals; observe third-party outputs; do not promise third-party outcomes.**

## P2 findings

### P2-01 — A single global AIO Score would be premature

Derived metrics are valid when traceable, but a composite score requires benchmark calibration, weighting rationale and reliability testing.

**Correction:** keep component metrics and diagnostics; defer a commercial global score.

### P2-02 — Market validation is not equivalent to methodology validation

The repository can validate methodology behavior without proving willingness to pay.

**Correction:** run 15–25 problem interviews, five manual audits, then three structured pilots before assuming recurring SaaS demand.

### P2-03 — Commercial ICP remains broad

**Recommended initial hypothesis:** public-facing people with multiple projects/brands and fragmented digital identity.

This remains a market hypothesis until interviews/pilots support it.

### P2-04 — Provenance architecture is strong but should remain modular

Provenance is valuable and well bounded, but it must not distract the pre-pilot core from entity representation and experimental traceability.

## What is already strong and should be preserved

1. Separation of canonical entities by stable IDs.
2. Explicit distinction between observation, interpretation, hypothesis and causal conclusion.
3. Historical observations are preserved rather than rewritten.
4. Source appearance is not treated as proof of causation.
5. First-party evidence is distinguished from independent validation.
6. Provenance does not overclaim copyright or authorship.
7. Retrieval, resolution, representation, citation and recommendation are already conceptually separated.
8. Negative and unchanged results are accepted as valid research results.
9. The Observatory and Entity Labs are separated conceptually.
10. AIO CODE is defined as the methodology; experiments occur within it.

## Freeze rule effective immediately

For any research window intended for comparison:

> **No material change without an Intervention ID or Confounder Log entry.**

A material change includes canonical text, schema, profile biography, public entity page, structured data, relationship definition, publication, cross-link, source addition/removal, experimental content or other change plausibly affecting retrieval/representation.

Repository documentation fixes that only clarify internal methodology must be tagged `methodology_correction` and recorded separately from entity interventions.

---

## Audit verdict

AIO CODE has crossed the threshold where building more architecture without governance creates more risk than value. The next defensible stage is:

**Evidence → Replication → Market Validation → Product.**

The project should proceed to pilot only after P0 findings are resolved and P1 controls are operational.
