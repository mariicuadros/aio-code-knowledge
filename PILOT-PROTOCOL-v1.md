# AIO CODE — Pilot Protocol v1

**Version:** 1.0  
**Date:** 2026-09-23  
**Status:** Canonical pre-pilot protocol

## 1. Purpose

This protocol defines how AIO CODE tests the methodology with external entities while preserving traceability, participant boundaries, evidence quality and comparability.

## 2. Pilot objective

The pilot does not attempt to prove that AIO CODE controls third-party AI systems. It tests whether the methodology can be applied consistently to different entities and whether documented interventions are followed by measurable representation changes under controlled observation conditions.

## 3. Initial pilot size

Recommended initial cohort: **3 external entities** with different structures.

Suggested topology:

- Pilot A: person/creator with a relatively simple identity.
- Pilot B: person + brand/project.
- Pilot C: person + multiple projects/roles with known ambiguity or fragmentation.

## 4. Pilot entry criteria

Each participant should have:

- a stable public name or entity identifier;
- at least two public information nodes;
- permission to review/modify selected first-party signals;
- willingness to preserve a pre-intervention baseline;
- agreement on what information can be public, private or anonymized.

## 5. Required participant input

- canonical name;
- aliases/alternate spellings;
- roles and projects;
- official links;
- platform profiles;
- desired and undesired entity associations;
- known confusion cases;
- supporting first-party documents;
- optional independent sources;
- consent/data handling choices.

## 6. Pilot stages

### Stage 0 — Intake

Create participant record and define scope.

### Stage 1 — Entity Audit

Build or verify:

- Entity Passport;
- canonical claims;
- relationship map;
- platform map;
- source consistency audit;
- known ambiguity list.

### Stage 2 — Baseline

Freeze:

- entity state;
- Prompt Registry version;
- systems tested;
- test conditions;
- response snapshots;
- representation rubric results.

### Stage 3 — Intervention Design

Select a limited number of controllable changes. Assign Intervention IDs. Declare expected effects and confounders.

### Stage 4 — Implementation

Apply only approved interventions and preserve before/after evidence.

### Stage 5 — Observation Window

Repeat comparable Observatory tests at declared intervals.

### Stage 6 — Measurement

Compare component metrics, not a single uncalibrated score.

### Stage 7 — Report

Deliver:

- entity consistency findings;
- source conflicts;
- relationship gaps;
- baseline representation profile;
- intervention log;
- observed post-intervention changes;
- negative/inconclusive results;
- limitations/confounders;
- next-step recommendations for controllable signals.

## 7. Data boundaries

Before work begins, record:

- participant ownership of their original data/content;
- what AIO CODE may store;
- what AIO CODE may publish;
- what may be anonymized/aggregated for research;
- retention period;
- exit/export/delete expectations;
- confidentiality level.

No private credentials should be stored in public research repositories.

## 8. Claims boundary

A pilot report may say:

- representation changed after a documented intervention;
- a change was replicated or not replicated;
- a system retrieved an official source;
- ambiguity decreased/increased under tested conditions;
- results were mixed or inconclusive.

A pilot report must not imply guaranteed causal control of a third-party model unless a separate causal standard has been met.

## 9. Success criteria

Methodology-level success is not "the AI said what we wanted." It includes:

- the protocol was executable;
- inputs and outputs were clear;
- baseline was preserved;
- interventions were traceable;
- observations were comparable;
- findings were reproducible enough to assess;
- uncertainty was recorded;
- the participant found the audit/report operationally useful.

## 10. Commercial validation fields

Separately record:

- time required per audit;
- implementation effort;
- participant's highest-value deliverable;
- willingness to pay for audit;
- willingness to pay for implementation;
- willingness to pay for recurring monitoring;
- objections;
- requested features.

Commercial data MUST NOT be confused with scientific validation.

## 11. Exit gate after first 3 pilots

Before building a full SaaS platform, answer:

1. Which repeated problem appeared across pilots?
2. Which part of the workflow was most valuable?
3. Which parts can be standardized?
4. Which interventions produced repeatable observations?
5. What remains entity-specific/manual?
6. Is recurring monitoring valuable enough to pay for?
7. What should software automate first?

## 12. Core rule

> Pilot the methodology before automating the methodology.
